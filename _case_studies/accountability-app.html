Personal project — Windows widget, downloadable

AccountabilityApp

A tab-and-app tracker that runs entirely on your own machine — no account, no cloud, nothing leaves the computer. It watches which app, browser tab, or editor file is actually in focus, and can quota-block (feature being tweaked) distracting categories (like Social Media or Games) once you've spent too long in them for the day. Finally, it can even generate a report about how long you spend (for my own personal use as a contract worker for work log purposes)

Why it needed to see more than "which app is open"

Most simple screen-time trackers stop at the app level: "Chrome was open for 3 hours." That number is close to useless, because Chrome being open is true whether you're reading documentation for work or scrolling social media: same app, completely different value. The same problem exists for a code editor: "VS Code was open" tells you nothing about what type of work was being done.

AccountabilityApp exists to fix that granularity gap — track the actual browser tab or the actual open file, not just the parent app — while keeping everything local as the best way to keep private since this is a personal tool easily downloaded for self. No account, no server elsewhere, no data leaving the machine. That local-only constraint shaped almost every technical decision below.

What it actually does

Tracking (see what's actually being used) and blocking (WIP)

Tracking — three separate clients report to one local server

A small server lives inside the desktop app itself, listening only on your own machine. A Chrome extension tells it "this tab is now active" every time you switch tabs. A VS Code (or Cursor) extension does the same for files. Neither extension talks to the internet — they only ever talk to the app sitting on the same computer.

Show the technical version

The Tauri backend runs a WebSocket server bound to 127.0.0.1:7734. Both extensions connect to it and send JSON events shaped like { source, tab_title, tab_url, timestamp }. The server closes out whatever session was previously open for that source and opens a new one, so at most one session per client is ever "open" at a time. A dedicated tab_sessions table (separate from the pre-existing app_sessions table) stores the result, with end_crash_tab_sessions() closing out any orphaned open rows on every app startup — so a crash mid-session can't leave a session open forever.

Blocking — a daily time budget per category, not per site

Rather than blocking a fixed list of sites, the app groups them into categories (Social Media, Games, more can be added) and gives each category a daily time limit. Once you've spent too long across everything in that category such as X.com and Reddit and Instagram all count toward the same "Social Media" budget — new tabs in that category get blocked, with a rotating set of deliberately annoying popups instead of one that's easy to click past (still in the works).

Show the technical version

Each category stores a daily limit in minutes, an enabled toggle, a manual pause toggle, and editable domain/app keyword lists. Usage is aggregated across tab_sessions, app_sessions, and any currently-open session, and evaluated per event via evaluate_tab_block. When a tab crosses the limit, the extension injects a blocking overlay and a rotating set of local popup deterrents (a fake ad, a rickroll-style redirect) that clean up automatically when the tab closes, navigates away, or loses focus.

What broke on the first real test, and what that taught me

All three of these only showed up once the feature was actually used end to end — not in any unit test.

The block only fired when you switched tabs — not while you sat and scrolled

The whole point of a time-based block is that it should trigger while you're still on the page, not just when you leave it. Instead, usage climbed correctly in the background, but the block overlay only ever appeared on the next tab switch — meaning you could sit on a blocked site indefinitely as long as you never switched away.

Show the technical version

The Chrome extension only sent tab events on onActivated (tab switch) and onUpdated (page load) — nothing fired while the user simply stayed on the same tab, and the block decision is only re-evaluated when the server receives an event. Fixed with a 15-second heartbeat inside ws.onopen: while connected, the extension re-sends the current active tab every 15 seconds, which re-triggers evaluate_tab_block on the backend. With a 60-second limit, the block now fires around 75 seconds in — one heartbeat interval of granularity, which was an acceptable trade for not needing a second, more complex timer mechanism.

Typing into the keyword editor kept bouncing the cursor to the start

The settings screen lets you edit which domains and app names count toward a category — but every keystroke reset the cursor to the beginning of the field, making it functionally impossible to type something like "x.com" one character at a time.

Show the technical version

Every onChange event called a Tauri command to save the value immediately, and the resulting store refresh re-rendered the input with the freshly-read database value mid-keystroke — overwriting whatever the user had just typed. Fixed by giving the input its own local draft state: onChange only updates the local draft, and the actual save fires once on onBlur, when the user clicks away. The lesson generalises: any input wired directly to a round-trip save on every keystroke is a cursor-jump bug waiting to happen the moment that round-trip is even slightly slower than typing speed.

The "annoying popup" deterrents closed themselves in under a second (unverified for now)

The blocking feature deliberately opens a couple of nuisance popup windows to discourage you from just closing the block overlay and moving on. In testing, those popups opened and then immediately closed themselves — the deterrent had no time to actually deter anything.

Show the technical version

Opening a new popup window with chrome.windows.create makes Chrome fire an onActivated event for the tab inside that new window. The extension's activation handler saw an unfamiliar tab become active and, reasonably from its own logic, assumed the user had switched away from the blocked tab — so it called stopBlocking, which closed every deterrent window it had just opened. Fixed by tracking deterrent window IDs in a set as they're created, and having the activation handler check a tab's windowId against that set before assuming a real switch happened. A same-origin side effect (a popup you opened yourself) triggering a listener meant to react to the user's actions was the actual root cause — not a timing bug.

Where it's honestly at

Tracking and category blocking both work end to end on Windows, with the Chrome extension shipped and tested (12/12) and the frontend covered too (35/35). The backend and WebSocket server already support a VS Code/Cursor client, but that extension itself isn't built yet — Chrome was the one built and proven first. There's also no "strict mode" equivalent yet: pausing a category is currently a simple toggle with no added friction, and pauses stay off until manually re-enabled rather than timing out on their own.

Turning tracked time into a report you could actually bill against

The original tracking was for self-accountability, but the same data — which app or tab was in focus, and for how long — is also exactly what you'd want as a record for contract work: proof of whether a fixed-price job actually took more or less time than it was quoted for. The feature that came out of this: press download, get a plain Markdown log of everything tracked since the last download, with a header and a subtotal.

Getting the download to actually work took two attempts. The first approach appeared to fail silently — nothing visible happened on click. It turned out to have worked the whole time; the file was just never confirmed by anything the app could see. That distinction mattered enough to switch to a mechanism that could actually prove success back to the user, rather than one that merely hoped it had worked.

Show the technical version

The first attempt used a plain browser-style download (Blob + <a download>). It did work — the file was written, just discovered afterward via File Explorer rather than through any signal the app received. The real gap: a browser download click and the file finishing writing are different events, and only the click is observable from script, even in a real browser. Replaced with tauri-plugin-dialog for a native Save-As picker, paired with a Rust command that writes the file via std::fs::write — here, the invoke() promise resolving is real proof the bytes were written, since it's the app's own code doing the write. That's what made an in-app "Saved" confirmation possible at all.

Investigated tracking AI-coding sessions directly — and chose not to build it

Windows Terminal is where most AI-assisted coding sessions actually happen, but the tracker had no way to see which tab was active inside it — unlike Chrome or VS Code. Two different ways to close that gap got seriously investigated: reading Windows Terminal's tab state directly, and hooking into Claude Code's own session events. Both turned out to have real, structural problems once traced through an actual example, not just a hypothetical one.

Rather than force either approach to work, the honest call was to leave that gap where it is. The report now shows Windows Terminal as a single lump of time with no per-tab detail, and the user relies on their own memory to separate real work from procrastination inside that block — a real limitation, stated as one, instead of a debatable heuristic pretending to be data.

Show the technical version

Windows Terminal renders its tab titles as custom XAML content and never writes them back to the underlying Win32 window title — confirmed by reading the tracking crate's source (a plain GetWindowTextW call, working exactly as intended) and corroborated by two open Microsoft repo issues confirming no public API exists to query tab state. The Claude Code alternative — hooking UserPromptSubmit to push events to the existing WebSocket server — was specced in detail, then traced through a real sequence (prompt → switch to Chrome → switch back) and found to produce overlapping, not sequential, time ranges: Claude Code hooks only fire on Claude Code's own internal events, never on "the user alt-tabbed away," which is the one thing the existing OS-level tracker can see for free and a hook structurally cannot.

A tracking toggle that looked off, but was quietly still recording

The app has a Start/Stop control meant to pause tracking entirely. It turned out to only ever pause half of it — browser and editor tab tracking kept being written to the database in the background regardless of what the toggle showed, for as long as the feature had existed.

The fix makes both tracking paths answer to the same switch, and — just as important — makes turning tracking back on resume cleanly without needing the browser extension to reconnect.

Show the technical version

The Start/Stop toggle only ever touched the app-level poller (state.tracker). The WebSocket server handling Chrome/VS Code events is spawned once at app launch, entirely independent of that toggle, so tab events kept being recorded regardless. Fixed with a shared tab_tracking_enabled flag checked inside the connection handler — while disabled, it skips recording but keeps the socket connection alive, so the extension doesn't need to reconnect once tracking resumes. Stopping tracking also now closes any currently-open tab session immediately, reusing the existing crash-recovery "close every open row" function rather than writing a new one.

Report generation at first try does not start on real time

A generated report showed an obviously wrong number — 17 hours of elapsed time for a session that had only really been running for 25 minutes. Chasing that display bug turned up something much bigger: the app's local database had been silently discarded and recreated from scratch (based on local deployment and using the .exe file updated after each build), over and over, for months, without ever telling anyone.

The app already had a safety mechanism for a specific failure case — if its encryption key ever goes missing, it backs up the unreadable old database under a timestamped filename and quietly starts fresh, rather than crashing. That mechanism was working exactly as designed. The actual problem was upstream of it: whatever was supposed to keep that key in place wasn't managing to, again and again, since the very first release — and nothing surfaced that fact until a feature that exposed real history (the report) made the gap visible for the first time. Still to fix.

Show the technical version

The app's encryption key is stored in the OS keyring; if get_or_create_key() can't find it, it renames the existing database aside as accountability.db.unreadable.<timestamp> and creates a new one with a fresh key — the documented, deliberate "safer key-loss handling" behavior from the first release. Checking the real app-data folder turned up 13 of these timestamped backup files dating back to April, meaning the key had been silently disappearing from the Windows keyring since launch. Root cause is still unconfirmed — it's an OS-level credential-storage question (antivirus interference, a Windows policy, or something about how the dev build launches are all still open possibilities), handed off for a direct check of Windows Credential Manager. Separately, the report's own display was fixed so a lost checkpoint can no longer produce a misleading window like "17h elapsed" — it now anchors to the first real tracked entry instead of the raw query boundary, even though the underlying query still searches the wider range so nothing is missed.

Built with Tauri, Rust, React, and SQLite — chosen specifically so tracking and blocking could run entirely offline, with no account and no data leaving the machine.
